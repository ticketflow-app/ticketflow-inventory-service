## 2. Decisiones

### Arquitectura de capas (REST)
- **Domain:** `Reservation`, `Availability`, `LocalityAvailability` (Java puro, sin cambios estructurales).
- **Application:** `CreateReservationUseCase`, `GetAvailabilityUseCase` (sin cambios en la interfaz).
- **Infrastructure (in):** Nuevos controladores bajo `/api/v1/events`, DTOs Java 21 Records, `GlobalExceptionHandler` reactivo (RFC 7807 / ProblemDetail).
- **Infrastructure (config):** `SecurityConfig` con JWT Bearer (`ReactiveJwtDecoder` vía `NimbusReactiveJwtDecoder`).

### Validación de entrada
- `jakarta.validation.constraints` (`@NotNull`, `@Min`) en `ReservationRequest.quantity`.
- Errores de validación retornan HTTP 400 con `ProblemDetail` y lista de `fieldErrors`.

### Manejo de excepciones (RFC 7807)
- `InsufficientAvailabilityException` → HTTP 409 Conflict (`INSUFFICIENT_AVAILABILITY`)
- `NotInitializedException` → HTTP 400 Bad Request (`NOT_INITIALIZED`)
- `ConstraintViolationException` / `WebExchangeBindException` → HTTP 400 Bad Request (`VALIDATION_ERROR`)
- `IllegalArgumentException` → HTTP 400 Bad Request (`INVALID_ARGUMENT`)
- `Exception` (genérico) → HTTP 500 Internal Server Error (`INTERNAL_ERROR`)

### Seguridad JWT
- Endpoints mutativos (`POST .../reservations`) requieren autenticación JWT Bearer.
- Endpoints de consulta (`GET .../availability`) permiten acceso anónimo (`permitAll`).
- CSRF y CORS deshabilitados (API stateless).
- `jwt.secret` configurable por variable de entorno `JWT_SECRET`.

## 4. Pruebas

### Pruebas de controlador reactivo (WebTestClient)
- `ReservationControllerWebFluxTest`:
  - **Happy path:** `POST /api/v1/events/10/sections/VIP/reservations` → HTTP 201 Created con `ReservationResponse` (reservationId, eventId, sectionId, quantity, status).
  - **Stock insuficiente:** `InsufficientAvailabilityException` → HTTP 409 Conflict con `title: "Insufficient Availability"` y `errorCode: INSUFFICIENT_AVAILABILITY`.
  - **No inicializado:** `NotInitializedException` → HTTP 400 Bad Request con `title: "Availability Not Initialized"` y `errorCode: NOT_INITIALIZED`.
  - **Validación (quantity = 0):** `@Min(1)` falla → HTTP 400 Bad Request con `errorCode: VALIDATION_ERROR`.
  - **Validación (quantity = null):** `@NotNull` falla → HTTP 400 Bad Request con `errorCode: VALIDATION_ERROR`.
  - **Consulta disponibilidad:** `GET /api/v1/events/10/sections/VIP/availability` → HTTP 200 OK con `AvailabilityResponse`.
  - **Consulta sección no existente:** `NotInitializedException` → HTTP 400 Bad Request.

### Pruebas de seguridad (WebTestClient)
- `SecurityWebFluxTest`:
  - **Sin JWT:** `POST /api/v1/events/10/sections/VIP/reservations` sin header `Authorization: Bearer` → HTTP 401 Unauthorized.

## 5. Integración

### Arquitectura hexagonal respetada
- **Domain:** Java puro, sin dependencias de frameworks de validación ni seguridad.
- **Application:** Casos de uso sin cambios en sus interfaces.
- **Infrastructure (in):** Controladores reactivos, DTOs, `GlobalExceptionHandler`, `SecurityConfig`.
- **Regla de dependencia:** `infrastructure → application → domain`.

### Tecnologías verificadas
- Java 21 Records para DTOs.
- Jakarta Validation (`jakarta.validation.constraints`).
- Spring WebFlux (`Mono<ResponseEntity<T>>`, `@RestControllerAdvice`, `ProblemDetail` RFC 7807).
- Spring Security Reactive (`SecurityWebFilterChain`, `ReactiveJwtDecoder`, `NimbusReactiveJwtDecoder`, `JwtAuthenticationConverter`).
- Spring Boot 4.1.1, Spring Cloud 2025.1.3.

### Sin operaciones bloqueantes
- Todo el flujo de API es reactivo (`Mono`, `WebTestClient`, `ReactiveJwtDecoder`).
- Cero uso de `block()` en rutas de producción (solo en pruebas de integración de Fase 3 con Testcontainers).
